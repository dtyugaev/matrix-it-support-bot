<functional_requirements>
### 1. Подключение и жизненный цикл комнаты
1.1. Бот подключается к Synapse по `access_token` (логин/пароль отключены на сервере).
1.2. Auto-join: бот автоматически принимает приглашение в комнату.
1.3. Сразу после входа в комнату бот отправляет приветствие и гостевое меню
     (для незарегистрированного пользователя): «Старт», «Помощь», «Обратная связь».
1.4. Если бота удаляют/кикают из комнаты — бот забывает эту комнату и удаляет
     соответствующую запись (room_id, user_id) из БД. При повторном приглашении в эту комнату
	 бот снова автоматически принимает приглашение и начинает работать как описано в п. 1.3.
1.5. Одна комната привязана ровно к одному пользователю (тому, кто нажал «Старт» и 
     зерегестрировался). Сообщения от других участников комнаты игнорируются ботом —
     при этом в ответ бот пишет оповещение, что комната зарегестрирована за другим пользователем.
1.6. Пользователь может создать новую комнату с ботом (например, если хочет
     несколько независимых сессий) — тогда он снова проходит `!start`,
     и в БД создаётся отдельная строка на пару (room_id, user_id).
     Таким образом один пользователь может иметь несколько активных комнат.
     Уведомления по заявкам Jira приходят сразу во все комнаты где зарегестрирован
     пользователь.
1.7. Если зарегестрированный пользователь выходит из комнаты, которая к нему привязана, 
     то бот удаляет эту связь (room_id, user_id) из БД и перестает отправлять уведомления
	 в эту комнату.

### 3. Текстовые команды
Доступные текстовые команды, остальное — через меню:
- `!start` — если пользователь+комната не зарегистрированы, создать запись
  в БД и показать главное меню. 
  Данные пользователя берутся из его профиля Matrix: displayname, userId, jira_login = localpart Matrix ID.
  email берется из Jira API, если email не удалось получить из Jira API, 
  то написать WARNING в лог и продолжить работу, т.е. email пользователя может быть пустым 
  и это не должно влиять на работу.
  Если запись уже существует — сообщить об этом и больше ничего.
  Подтверждение по почте не требуется.
- `!create` — создать заявку в Jira
- `!status <KEY>` — статус заявки в Jira по ключу
- `!list` — мои заявки в Jira
- `!menu` — показать главное меню:
  - для незарегистрированного пользователя в комнате — гостевое меню (см. 1.3);
  - для зарегистрированного — «Создать заявку», «Узнать статус заявки»,
    «Мой профиль», «Помощь», «Обратная связь».
- `!help` — справка по всем командам и краткое объяснение навигации по меню.

При написании пользователем неизвестной команды, необходимо вывести сообщение 
со справкой по работе бота из раздела `!help`.

### 4. Интеграция с Jira
4.1. Создание заявки, получение списка своих заявок и статусов, изменение статуса заявки,
     оставление комментариев, получение вложений — логика идентична эталонному боту, 
	 адаптированная под сценарии меню Matrix.
4.2. Уникальный идентификатор пользователя в Jira - это его jira_login, 
     который = localpart Matrix ID. Все запросы к Jira API осуществляются через jira_login.
	 Почта в Jira может повторяться и не является уникальным идентификатор пользователя.
4.2. Уведомления об изменении статуса заявки приходят через плагин Jira
     Status Listener; параметр в конфиге `jira.status_listener_url`.
4.3. Частота обновления информации из Jira — задаётся в конфиге
     (`jira.poll_interval_seconds`).
4.4. Вложения из Jira, которые бот прикладывает при выводе статуса заявки,
     должны автоматически удаляться через настраиваемое время
     (`jira.attachment_ttl`):
     - удалить сообщение с медиа из чата (Matrix redact/delete события);
     - удалить локальный файл из папки бота;
     - удалить файл из медиа-хранилища Synapse через Admin API.
     Приоритет для Admin API: сначала пробовать под собственным токеном бота
     (если у аккаунта бота есть права администратора сервера), при ошибке —
     fallback на отдельный `admin_access_token` из конфига.
4.5. Типы заявок которые отображаются в разделе меню "Список моих заявок"
     настраивается параметром `issue_types_for_list`. Полный список возможных типов заявок
	 возьми из эталонного Telegram-бота (см. `<reference_project>`)
4.6. В разделе меню "Найти заявку по номеру" отображать информацию о заявке всегда,
     в каком бы она статусе не была (открыта или закрыта). 
	 Если у пользователя Jira нет доступа к заявке, 
	 то написать об этом сообщение и вернуться на предыдущий шаг меню.

### 5. Управление заявками: поиск и работа со статусом
5.1. **Поиск заявки.** После выбора пункта «Узнать статус заявки» бот
     предлагает подменю с двумя вариантами поиска:
     - «📋 Список моих заявок» — бот выводит постранично список заявок пользователя
       (текст + номер каждой заявки). Смотри пример *Ваши заявки* в пункте 2.6.
     - «🔢 Найти заявку по номеру» — бот просит ввести номер в формате `IT-1234`
       (валидация формата на стороне бота: префикс проекта + дефис + цифры;
       при некорректном вводе — понятное сообщение об ошибке и повторный
       запрос, без выхода из сценария).
     Логику получения списка/поиска заявки по номеру взять из эталонного
     Telegram-бота (см. `<reference_project>`), адаптировав вывод под
     текстовый формат Matrix.

5.2. **Действия с найденной заявкой.** После того как заявка найдена и
     открыта, бот показывает подменю доступных действий. Состав этого
     подменю **динамический** — зависит от текущего статуса заявки в Jira,
     а не фиксирован:
     - «📝 Предоставить информацию» — показывается только если заявка в
       статусе *«Запрос информации»* (точное имя статуса в Jira уточнить
       при анализе эталонного проекта); выбор пункта открывает форму ввода
       текста/вложений, которые уходят комментарием в Jira.
     - «🔁 Переоткрыть» — показывается, если заявка в статусе, означающем
       предложенное или закрытое решение, и пользователя оно не устроило;
       переводит заявку обратно в работу через Jira API.
     - «✅ Подтвердить решение» — показывается в том же статусе, что и
       «Переоткрыть» (как альтернативный исход); подтверждает и закрывает
       заявку через Jira API.
     - «🗨️ Добавить комментарий» — доступно всегда; добавляет комментарий к
       заявке через Jira API (это поведение настраивается параметром `always_allow_comment`,
	   если значение false, то взять логику из эталонного Telegram-бота).
     - «📎 Получить вложения» — доступно всегда, когда у заявки есть
       вложения; бот скачивает их из Jira, отправляет в чат Matrix в zip архиве и
       регистрирует для последующей автоматической очистки согласно
       `jira.attachment_ttl` (см. п. 4.4).
	   Все вложения заявки отдаются одним zip-архивом.
     Обязательно зафиксируй в разделе "Анализ" таблицу соответствия
     `статус заявки в Jira → какие из пяти действий доступны`, построенную
     на основе реальной логики эталонного бота (а не предположений), и
     реализуй проверку доступности действия на основе этой таблицы перед
     тем, как выполнять его.

### 9. Централизованное хранение текстовых сообщений бота
9.1. Все фразы, которые бот показывает пользователю или администратору

<non_functional_requirements>
- Секреты (токены, пароли БД) — только в конфиге, не хардкодить, не логировать
  в открытом виде.
- Логирование без ротации, но с понятными уровнями
  (DEBUG/INFO/WARNING/ERROR) и настраиваемым форматом с таймстампом.
- Устойчивость к недоступности Jira/Synapse: таймауты и повторные попытки
  с backoff для сетевых вызовов, без падения основного цикла бота.
  Если авторизация Jira/Synapse прошла неуспешно, то написать ошибку в логах.
- Код читаемый, с докстрингами на ключевых модулях/функциях, типизирован
  (type hints).
</non_functional_requirements>
