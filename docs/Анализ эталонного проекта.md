# Анализ эталонного проекта `otr_bot` (ветка `fix_notif`)

Источник: <https://github.com/dtyugaev/otr_bot> (публичный репозиторий, дефолтная ветка
`fix_notif`, 12 коммитов, Python 99 %). Анализ выполнен по исходному коду: прочитаны
`bot.py`, `bot_core/*`, `core/*`, `modules/*`, `service/*`, `update/database_create.sql`,
`pre_install.py`, `requirements.txt`.

## 2. Схема БД эталонного проекта (SQLite, `update/database_create.sql`)

| Таблица | Поля | Назначение |
|---|---|---|
| `users` | `tg_id INTEGER` (уникальный индекс), `fio TEXT`, `email TEXT`, `approved INTEGER`, `login TEXT` | Профиль пользователя; `login` — логин Jira, `approved` — подтверждение по коду из письма |
| `privilege` | `tg_id INT NOT NULL`, `supervisor INT DEFAULT 0` | Привилегия просмотра любых заявок |
| `audit` | `tg_id INT`, `fio TEXT`, `action TEXT`, `date TEXT` | Журнал действий пользователя |
| `stats` | `date TEXT`, `action TEXT` | Статистика действий (`STATS_ACTIONS`) |
| `code` | `tg_id INT` (уникальный индекс), `code INT` | Одноразовый код подтверждения регистрации; таблица пересоздаётся при старте |
| `spammers` | `tg_id INT` (уникальный индекс) | Заблокированные за спам пользователи |
| `errors` | `time_error`, `error` | Ошибки (используется в `save_error()`) |

Связей на уровне FK нет: все таблицы связаны логически по `tg_id`.

## 3. Логика команд и сценариев (пошаговый псевдокод)

### 3.1 `/regme` — регистрация
```
1. audit("Попытка зарегистрироваться")
2. если is_user_approved(tg_id): "Вы уже зарегистрированы" + главное меню -> выход
3. если is_user_registered(tg_id): "Вам уже отправлен код" -> состояние wait_code -> выход
4. запросить корпоративную почту -> состояние wait_email
5. wait_email: валидация наличия "@"
   5.1 jira.search_users(email) -> найти пользователя с точным совпадением emailAddress
   5.2 если не найден: "Некорректный адрес почты..." -> выход
   5.3 new_user_profile(tg_id, {fio: displayName, email, login: user.name}), approved = 0
   5.4 generate_reg_code(tg_id) -> случайный код 1111..9999 -> письмо через SMTP
   5.5 состояние wait_code
6. wait_code: сравнить введённый код с кодом из БД
   6.1 неверно: счётчики error_code/spam; >3 ошибок -> новый код; >10 попыток -> spammers
   6.2 верно: approve_user(tg_id) -> "Профиль подтверждён" + главное меню
              + сообщение в админ-чат "Зарегистрирован новый пользователь"
```

### 3.2 «Создать заявку»
```
1. "Введите тему заявки" -> wait_subject
2. wait_subject: только текст, длина <= 255 -> сохранить -> "Введите описание и приложите вложение" -> wait_desc
3. wait_desc: тип photo/document -> скачать вложение в storage/<tg_id>/; описание = caption либо text
4. вывести "Проверьте введённые данные" (тема, описание, файл) + кнопки Да/Нет -> wait_accept
5. accept = no -> "Отмена операции"
   accept = yes -> jira.create_issue(project="IT", issuetype=10000, reporter=login, summary, description)
                   + add_attachment(файл) + удаление локального файла
6. "Заявка <KEY> зарегистрирована" + stats("Создание заявки")
```

### 3.3 «Список моих заявок»
```
1. audit("Нажал кнопку список заявок")
2. jira.get_all_user_issues(email): JQL
   project in (IT) AND reporter in (<localpart почты>) ORDER BY createdDate
3. сортировка по группам статусов: Запрос информации -> Предложено решение -> Открыта ->
   В работе -> прочие; статус "Закрыто" в список не попадает
4. нарезка по 5 заявок на страницу
5. вывод inline-кнопок "<KEY> | <статус> | <тема>" + строка пагинации "◀ n из N ▶"
6. callback issue:<KEY>:<page> -> открыть карточку заявки
```

### 3.4 «Найти заявку по номеру» / статус заявки
```
1. "Введите номер заявки в формате: IT-123" -> состояние enter_issue
2. jira.get_issue_from_id(KEY): поля created/updated -> формат dd.mm.YYYY HH:MM:SS,
   description очищается от {color} тегов, комментарии — только без visibility, последний комментарий
3. проверка доступа: issue.email == user.email, иначе нужна привилегия supervisor,
   иначе "Некорректный номер заявки или у вас отсутствует доступ..."
4. вывод карточки (номер, тема, даты, статус, количество вложений)
5. вывод последнего комментария + динамическая клавиатура действий
6. stats("Открыть заявку")
```

### 3.5 Действия по заявке (`processing_issue`)
```
Добавить комментарий:   запросить текст/вложение -> jira.add_comment("(Заявитель) [ФИО]: <текст>")
Предоставить информацию: проверить, что статус всё ещё "Запрос информации" ->
                        switch_status("Ответ для робота") с комментарием и вложением
Переоткрыть:            проверить статус "Подтверждение решения" -> switch_status("Переоткрыть")
Подтвердить решение:    switch_status("Закрыть", комментарий "Пользователь подтвердил решение заявки")
Получить вложения:      jira.get_issue_attachments_file(KEY) -> system.zip_file() -> отправка документа
                        -> локальное удаление архива
После любого действия карточка заявки перечитывается и выводится заново.
```

### 3.6 Уведомления (`service/monitoring_issue`)
```
while True:
  1. get_event(): GET config[service][event_url] с cookies JSESSIONID/atlassian.xsrf.token
  2. events -> dict по issueKey
  3. generate_notification: statusId -> имя статуса по карте statused
     - "Запрос информации"   -> "запрошена дополнительная информация"
     - "Предложено решение"  -> "предложено решение"
     остальные статусы игнорируются
  4. по reporterEmail найти профили в БД (get_user_profile_from_attr('email', ...));
     если профиль не найден -> ERROR "Не найден профиль в бд <email>"
  5. отправить всем найденным пользователям сообщение + кнопку "Открыть заявку"
  6. delete_all_event(): DELETE <event_url>/<id> по каждому событию
  7. ошибки -> сообщение в админ-чат + архив логов; sleep 30 c (при сбое 600 c)
```

## 4. Механизм приёма уведомлений от Jira

* Используется **плагин Jira Status Listener** — REST-эндпоинт, который отдаёт очередь
  событий смены статуса. В эталонном проекте адрес хранится в `config.ini` в секции
  `[service]` параметром `event_url`; в новом боте — `jira.status_listener_url`.
* Механизм — **поллинг очереди событий** (не вебхук): цикл `GET` каждые 30 секунд,
  затем `DELETE /<id>` для каждого обработанного события, то есть очередь вычитывается
  «насухо». Авторизация — cookies (`JSESSIONID`, `atlassian.xsrf.token`), полученные из
  сессии библиотеки `jira`, плюс заголовок `X-Atlassian-Token: no-check`.
* Формат события (по коду обработчика): `id`, `issueKey`, `statusId`, `userName`,
  `reporterEmail`.
* Отдельные переходы «Ответ для робота» и «Переоткрыть» используются именно для того,
  чтобы Jira не рассылала собственные уведомления по действиям, инициированным ботом.

## 6. Матрица «статус заявки в Jira → доступные действия»

Построена по реальному коду `modules/private/find_issue/keyboards.py::kb_processing_issue`
и карте переходов `core/core_jira/api.py::complete_switch_statused`. Обратите внимание:
статус, который в интерфейсе бота называется «Решение предложено», в Jira называется
**«Подтверждение решения»** — именно он проверяется в коде.

| Статус заявки в Jira | 📝 Предоставить информацию | 🔁 Переоткрыть | ✅ Подтвердить решение | 🗨️ Добавить комментарий (`always_allow_comment: false`) | 📎 Получить вложения |
|---|---|---|---|---|---|
| Зарегистрировано | — | — | — | + | + (если вложения есть) |
| Открыта | — | — | — | + | + |
| В работе | — | — | — | + | + |
| Запрос информации | **+** | — | — | — | + |
| Ответ предоставлен | — | — | — | + | + |
| Ожидает решения | — | — | — | + | + |
| Отложено | — | — | — | + | + |
| Согласование ФЗ / УИБ, Прокомментировано УИБ, Передано на 3 линию | — | — | — | + | + |
| Переоткрыто | — | — | — | + | + |
| **Подтверждение решения** (решение предложено) | — | **+** | **+** | — | + |
| Закрыто | — | — | — | — | + |
| Спам | — | — | — | + | + |

При `always_allow_comment: true` (значение по умолчанию нового бота) пункт
«🗨️ Добавить комментарий» доступен во всех статусах, включая «Запрос информации»,
«Подтверждение решения» и «Закрыто».

Переходы Jira, которые выполняет бот:

| Действие бота | Переход Jira | Допустимые исходные статусы | Целевой статус |
|---|---|---|---|
| Предоставить информацию | `Ответ для робота` | Запрос информации | Ответ предоставлен |
| Переоткрыть | `Переоткрыть` | Подтверждение решения, Закрыто | Переоткрыто |
| Подтвердить решение | `Закрыть` | Подтверждение решения | Закрыто |

Матрица реализована в `src/jira/transitions.py` (`available_actions`, `is_action_available`)
и проверяется **до** выполнения действия; тесты — `tests/test_transitions.py`.

## 7. Прочие важные наблюдения

1. **Соответствие «пользователь ↔ чат»**: в Telegram чат тождественен `tg_id`, поэтому
   отдельной сущности «комната» не было. В Matrix одна и та же учётная запись может
   иметь несколько комнат, поэтому ключ БД изменён на пару `(room_id, user_id)`.
2. **Идентификация в Jira**: эталонный бот искал пользователя по почте
   (`search_users(email)`), а в JQL подставлял `email.split("@")[0]`, то есть фактически
   логин. В новом боте это закреплено явно: `jira_login = localpart` Matrix ID, а почта —
   необязательный атрибут (п. 4.2 ТЗ).
3. **Статус «Закрыто»** в эталонном списке заявок отбрасывался. В новом боте перечень
   статусов вынесен в конфигурацию `jira.issue_types_for_list`, а поиск по номеру
   показывает заявку в любом статусе (п. 4.6 ТЗ).
4. **Ограничения Telegram**: лимит сообщения 4096 символов вынуждал нарезать комментарии
   (`com_chunk`), лимит 15/50 МБ — на вложения. В Matrix лимиты другие, поэтому нарезка
   сохранена, но с порогом 30 000 символов (`src/utils/text.py::split_message`).
5. **Аудит и статистика** велись в двух таблицах (`audit`, `stats`) с дублированием.
   В новом боте одна таблица `audit_log`, статистика считается агрегатом по ней.
6. **Sentry** использовался для трейсинга; в новом проекте не переносится (см. ниже).
7. **Обработка ошибок**: каждый хендлер эталонного бота оборачивает логику в
   `try/except` c отправкой архива логов в админ-чат. В новом боте вместо архива логов
   в комнату администраторов отправляется текст ошибки (события настраиваются), а полный
   журнал доступен командой `!admin logs`.

## 8. Функции эталонного проекта, не перенесённые в `matrix-it-support-bot`

| Функция эталонного бота | Причина непереноса |
|---|---|
| Регистрация по почте с кодом подтверждения (`/regme`, таблицы `code`, отправка письма через SMTP) | Прямо исключено ТЗ (п. 3): подтверждение по почте не требуется, данные берутся из профиля Matrix, `jira_login` = localpart MXID |
| Поле `approved` и проверка `IsUserApprove` | Нет процедуры подтверждения — пользователь считается зарегистрированным сразу после `!start` |
| Таблица `spammers` и антиспам-счётчики попыток ввода кода | Логика существовала только для защиты процедуры подтверждения кода, которой больше нет. Роль «защиты от чужих» выполняет привязка комнаты к одному пользователю (п. 1.5) |
| Привилегия `supervisor` (таблица `privilege`, команды `/install_priv`, `/remove_priv`) | В ТЗ нового бота нет ролевой модели пользователей. Эквивалент сохранён: администраторы бота из `administration.admins` видят любую заявку |
| Sentry (`sentry-sdk`, трейсинг транзакций) | В ТЗ не заявлено, требует внешнего сервиса и передачи данных наружу; наблюдаемость закрыта журналом с уровнями и комнатой администраторов |
| Выгрузка пользователей/аудита в XLSX (`XlsxWriter`) | Заменена выгрузкой в CSV (`!admin export_users`), чтобы не тянуть дополнительную зависимость; данные и назначение те же |
| Отправка архива логов при каждой ошибке пользователя | Шумно и содержит персональные данные; вместо этого — настраиваемые события в комнате администраторов (п. 8.4) и команда `!admin logs` |
| Inline- и reply-клавиатуры Telegram, `callback_data` | В Matrix нет inline-кнопок: заменены текстовыми меню с эмодзи-реакциями (п. 2 ТЗ) |
| Пересылка сообщения обратной связи (`forward_message`) | В Matrix нет forward: текст обращения копируется в комнату администраторов с указанием автора, комнаты и идентификатора обращения |
| `/status` как отдельная пользовательская команда, файл `storage/status` | Перечень пользовательских команд зафиксирован в п. 3 ТЗ; информация о версии и uptime доступна администраторам через `!admin status` |
| Команда `/get_chat_info` | Служебная отладочная команда Telegram, не имеет смысла в Matrix |
| Скрипты `update_bot.sh`, `todolist.py`, файл `.bash_history` в репозитории | Служебные артефакты рабочей станции разработчика; заменены каталогом `deploy/` (systemd, Docker) |

## 9. Что дополнено относительно эталона (по требованиям ТЗ)

* Подключение к Synapse по `access_token`, auto-join, «забывание» комнаты при кике (п. 1).
* Меню на эмодзи-реакциях с настройкой формата вывода (`menu_items_as_list`, `markup`).
* Несколько независимых комнат на одного пользователя и веерная рассылка уведомлений.
* Автоочистка вложений по TTL в трёх местах: комната, диск бота, медиа-хранилище
  Synapse (Admin API с fallback-токеном).
* Единый `config.yaml` с комментариями к каждому параметру и выбор БД sqlite/postgresql.
* Централизованное хранилище фраз `src/texts.py` (без хардкода строк в логике).
* Настраиваемые события комнаты администраторов (`administration.notify_events`).
